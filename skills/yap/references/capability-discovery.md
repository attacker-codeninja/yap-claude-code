# Discover the editing toolbox

Before choosing the workflow, ask internally: **What tools, skills, models and
asset libraries can I use beyond the Yap skill and product?** Inspect the tools
and skills exposed by this session, relevant local executables and retained project
assets. Discovery is read-only; presence is not execution readiness.

Save a short inventory in the task workspace: capability, actual provider/path,
readiness evidence, provenance and intended use. Cover what this brief needs for
understanding, asset creation and verification. Avoid listing every installed
program. An account connection, working executable or existing prepared model is
evidence; a product name in a reference is not.

Record Yap independently from the skill:

- Save `command -v yap`, relevant operation help, and the raw `service.health`
  reply. Its advertised version identifies the running service; null means
  unknown. If advertised, `service.tools` identifies the selected app's Node
  and verified media tools. Help alone does not prove native readiness.
- Resolve the skill folder actually loaded by this session, including discovery
  links. Record its path and hashes of the instructions/helpers you use. Record
  a pinned source commit or installer receipt only when retained evidence proves
  it; otherwise say origin unknown. A repo checkout or latest app version does
  not prove that an independently installed skill is current. Read
  [skill lifecycle](skill-lifecycle.md) only when inspecting or updating that
  installation; discovery does not authorize refresh.

Use the installed CLI's actual schemas. If the skill describes an absent operation,
report the mismatch and choose an available approach that meets the brief. Never
claim planned capabilities exist or invent a provider's paths/readiness. Keep
external requests/results and retained generated bytes with their provider/model
identity; a stochastic generation recipe does not promise identical regenerated
assets.

For feedback review, discover `transcript.review`, `cursor.render` and their
advertised retry/readiness behavior in the installed operation help. `transcript.review`
is the convenience combination of `transcript.transcribe` and `transcript.get`
for bounded transcription; call it directly. If it
reports `MODEL_NOT_PREPARED`, use the returned model purpose, download scope and
size to ask the user before calling `model.prepare`. Record whether each
operation is present and its exact CLI/service version. Newer skill text must not
be treated as proof that an older release implements these operations; fall back
to the explicit evidence pipeline when they are absent.

Use useful available capabilities. Call a requested Yap feature directly; do not
use `model.list`, `model.status` or `model.prepare` as a preflight. If the feature
returns `MODEL_NOT_PREPARED`, inspect the returned model ID, purpose, download
scope/size and reason, ask the user whether to acquire it, then call
`model.prepare` only after an explicit yes. Poll `model.status` and retry the
same request. `model.prepare` acquires and verifies model/runtime files; it does
not perform inference. If the error omits those details, report the concrete gap
instead of guessing a download or source.

Recommend a missing **external** capability only when it
would materially improve the requested result or is required—such as an explicit
AI-video request without a usable video generator. Explain the gap and the smallest
setup that would address it. Do not install external tools/models or set up
accounts by default. Continue independent work and deliver the best checked
candidate with the remaining gap explicit. Do not replace requested AI footage
with unrelated stock footage and call the request satisfied.

For current read-only helper recipes, use [helper examples](helper-examples.md).
For autonomous review and repair, use [editorial checks](editorial-checks.md).
